# OpenXDR 统一启动的欺骗引擎

DYGK 跟随 OpenXDR 的主编排启动，共用安装目录的 `.env`。平台自动识别实际运行版本，按登记下发配置、分配实例和签发身份；运维不需要逐个填写连接器参数。引擎产物可以独立升级，OpenXDR 的资产、组权限、审计和事件研判保持统一。

## 启动

在 OpenXDR 已有 `.env` 中启用模块；已有其他 Compose profile 时追加 `dygk`：

```dotenv
COMPOSE_PROFILES=dygk
```

继续使用原启动命令：

```bash
docker compose up -d
```

源码编排会构建 `integrations/dygk/Dockerfile`；安装编排使用独立镜像。默认关闭该 profile，不影响原有 OpenXDR 部署。生产可在同一 `.env` 中用 `DYGK_VERSION` 锁定引擎镜像标签，独立于 `OPENXDR_VERSION`。当前镜像发布尚受上游分发授权约束，见文末。

容器地址、控制通道和数据卷由主编排设置。平台与引擎使用仅挂给这两个服务、0700 目录和 0600 socket 的 Unix 控制通道，不增加网络管理端口，不向引擎提供数据库密码或平台凭据主密钥。控制通道和托管进程面向 Linux 容器。

## 控制台使用

1. 在「资产 → 诱饵管理」为已分组资产登记 HTTP 诱饵。默认托管端口为 18080，主编排默认预留 18080–18179；多个站点使用不同端口。
2. 打开「引擎配置与升级」，保持「平台统一启动」。已启动引擎的实际版本会自动出现，无需手动粘贴版本摘要。
3. 选择观察、来源封禁或合成假后台，以及独立站点或业务网关。保存修订后，平台自动分配实例、签发运行身份，运行端取得配置后启动。
4. 停止、升级和恢复历史配置均在同一页面操作。停止请求不等于已退出，升级需等待实例确认。

平台托管绑定的是所保护站点的资产，实际监听位于引擎服务中。`running` 是运行端回报，不证明 DNS、入口代理、防火墙或云安全组已打通。主编排默认只将预留端口绑定到宿主回环；需要对外服务时，在同一 `.env` 配置 `DYGK_BIND_IP`、`DYGK_PORT_RANGE` 并按站点接入现有反向代理或云端入口。

版本准入和令牌工具保留在高级入口，供兼容原生或远端运行包使用；平台托管路径不要求用户操作这些内部身份参数。

## 运行实现与云端构建

| 组成 | 位置 | 作用 |
| --- | --- | --- |
| 原生引擎 | `server/deception/` | 迁出的 SSH、HTTP 兼容、Linux 文件监视和有限模拟 Shell，模板与行为测试只有一份 |
| 平台契约与 SDK | `server/deception/contract`、`sdk` | 能力、白名单事实、运行认证与租约，不依赖 Ent 或平台数据库 |
| Web 连接器与托管管理器 | 本目录 `web/` | DYGK Web 调用、持久补传和平台自动启动 |
| 平台控制面 | `server/internal/api/deception*.go` | 组范围、版本与修订、内部实例分配、审计和待复核事件 |

Go 沿用仓库 `server/go.mod`，没有本地 `replace`、额外工作区或构建机绝对路径。DYGK Web 锁定完整 commit 和文件摘要，在镜像构建阶段准备；运行时只验证包内依赖，不下载代码。Node 24 在独立引擎镜像中，不改变 Pi 的 Node 环境。

### 源码缓存和 Git 管理

当前采用构建时源码集成：本目录既有 OpenXDR 维护的接入代码，也可能存在准备脚本生成的 DYGK 上游源码缓存。Git 忽略缓存表示它不随项目提交，磁盘上仍然会有这些源码。

下表路径相对本目录：

| 内容 | 用途 | Git 管理 |
| --- | --- | --- |
| `web/`、`scripts/`、`tests/` | OpenXDR 的连接器、托管管理器、事件导出适配、构建与接入测试 | 纳入版本管理 |
| `Dockerfile`、`package.json`、`upstream.lock.json` 等 | 构建入口、运行元数据、上游版本和文件摘要 | 纳入版本管理 |
| `.downloads/<commit>/` | 自动下载的上游 Git checkout，供准备和更新脚本使用；指定已有源码时可以不生成 | 由 `.gitignore` 排除 |
| `.upstream/<commit>/` | 适配后的上游源码缓存，包含 `lib/` 及测试所需的 `tests/`、`examples/` 和部分 `experiments/` 文件 | 由 `.gitignore` 排除 |
| `*.sqlite*`、`runtime-state/` | 开发时产生的运行状态；部署时状态保存在命名卷 | 由 `.gitignore` 排除 |

新克隆的 OpenXDR 不含这些上游缓存，需要在准备或镜像构建阶段按锁文件获取源码。根目录 `.dockerignore` 同样排除开发机的 `.downloads/` 和 `.upstream/`；镜像构建在构建阶段重新准备依赖，不依赖开发机缓存或目录。

`stage-runtime.mjs` 将上游的 `lib/`、`package.json` 和 `.prepared.json` 放入最终运行包，再加入 OpenXDR 的接入代码和产物清单。上游的 `tests/`、`examples/`、`experiments/` 和 `.git/` 不进入最终运行镜像。镜像内仍包含运行所需的 DYGK 核心源码，运行时无需访问上游仓库。

不要直接修改 `.upstream/` 中的代码作为长期维护方式；需要调整行为时修改接入代码或准备脚本，更新上游时使用后文的候选更新流程。“独立升级”指引擎运行产物可以独立交付；上游内部结构变化时，仍可能需要更新源码适配和平台契约。

### 构建凭据和持久卷

上游当前匿名读取返回 404。源码部署需在同一 `.env` 配置有该仓库读取权限的 `DYGK_UPSTREAM_TOKEN`；CI 在仓库 Secrets 中设置同名项。主编排通过 BuildKit 构建 secret 临时提供凭据，令牌不进入镜像、运行环境或源码 URL。安装编排使用已构建镜像，运行时不需要上游令牌。公开上游可将此构建项设为空。

引擎状态使用主编排命名卷，按登记隔离数据子目录；控制通道使用另一命名卷。Kubernetes 等环境对应使用同一组平台配置、受限共享控制卷和引擎持久卷。分离到不同 Pod 或节点时应改用高级远端运行协议和受信 HTTPS，不能把 Unix socket 路径当网络地址。

## 当前能力与事实

DYGK 基线为 `bd8515a0b930f530eec0d13955fe502d8c8e9e25`，包含正式库的有界递归归档、模拟凭据验证、来源封禁和 `quarantine` 假后台。连接器不启用研究用客户端挑战或采集自报模型身份。

上游事件导出扩展在同一 SQLite 事务写事实、稳定 UUID 和流序号；表单状态推进与触发事实、局部封禁与其事实分别同事务保存。游标支持保留缺口检查，连接器持久保存积压，得到平台逐条确认后才删除。假后台的来源 TTL、已揭示入口和请求预算持久化，重启不重置预算。适配位置变化或出现未知事实类型时，候选构建拒绝继续。

平台默认只接收白名单事实、发生时间、计数和不透明会话标识，不包含 IP、Cookie、凭据、请求体或原始会话 ID。访问轨迹有抽样，观察条数不等于实际访问次数。有效模拟凭据触发按修订和会话只开一次复核单；仅有诱饵观察不能触发自动主机隔离。

## 业务入口与故障行为

独立站点只保护自身。使用 `gateway` 时，业务必须统一经过引擎入口，原业务端口不能继续对访问者开放。可信代理只接受明确 IP；共享 NAT 或代理可能使多个用户共用一个来源出口。

当前网关支持有界 HTML 注入，JSON、SSE、压缩和超大 HTML 沿用上游透传；WebSocket 明确返回 501。先以观察模式验证实际站点兼容性，再启用来源封禁或假后台。

平台暂时失联容忍至最后成功核验后 60 秒。独立诱饵停止；业务网关停止生成诱饵并透传原 upstream，已有封禁或隔离保持至原 TTL，不新增或延长动作。明确撤销或迁组立即停止或降级；托管版本被明确停用时停止实例，操作前应安排业务入口。恢复后需核查并重新启动，不能将透传状态当作健康欺骗引擎。

## 上游更新与部署回退

更新候选版本只修改锁文件和必要适配，使用完整上游 commit：

```bash
node integrations/dygk/scripts/update-upstream.mjs <完整commit>
```

脚本检查源码摘要、事件契约、适配位置和上游行为；失败恢复锁文件。继续通过平台端到端和兼容检查后发布独立引擎运行包，原生与 Web 运行实现不再复制进平台内部包。

部署升级时，先在控制台停止旧实例，再在同一 `.env` 更新 `DYGK_VERSION`，通过主编排拉取并更新引擎服务。新运行包自动回报版本，控制台选择对应修订后自动启动。平台修改修订不直接控制 Docker，也不会用未准入的未来能力自动改变正在运行的策略。

恢复历史配置会创建新修订，需配套恢复其产物。旧修订有未确认积压时禁止转报到新修订；状态格式不兼容时拒绝原地换版，需要新登记和明确迁移。升级前使用存储系统制作可恢复快照，不能仅回退镜像就假定 SQLite 已恢复。

## 验证与发布

```bash
go -C server test ./deception/... ./internal/decoy
node integrations/dygk/scripts/prepare-upstream.mjs
npm --prefix integrations/dygk test
npm --prefix integrations/dygk run test:upstream
```

Node 需要 24；上游测试还使用 Python 3 和 POSIX shell。Linux CI 验证原生行为、上游行为、实际 Node 到 PostgreSQL 复核闭环，以及托管引擎通过平台配置自动启动。Windows 上游测试存在清理仍打开的 SQLite 文件的权限限制，不能据此跳过 Linux CI。

独立发布工作流为 `.github/workflows/deception-engine.yml`，由手动运行或 `dygk-v*` 标签触发。DYGK 当前为 `UNLICENSED`，公开镜像发布仅在确认授权并配置仓库变量 `DYGK_DISTRIBUTION_AUTHORIZED=true` 后开启。当前改动未发布、未部署；本机环境没有 Docker，镜像构建仍需 Linux CI 验收。
