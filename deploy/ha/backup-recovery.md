# 节点外备份与恢复验收

`backup.py` 从当前主库读取一致性逻辑快照，将角色、运行时配置和数据库导出到执行机器。
不占用生产节点的备份磁盘，不安装定时任务，不删除旧备份。需要 Python 3、SSH 和节点 Docker 权限。
指定主库，使用全新的私有输出目录：

```sh
python3 deploy/ha/backup.py --node <主库SSH地址> --output /安全磁盘/openxdr/20261022
python3 deploy/ha/verify-backup.py --backup /安全磁盘/openxdr/20261022
```

执行机器需预装对应主版本的 PostgreSQL Docker 镜像（默认 `postgres:16`），并在备份和恢复前分别
预留至少数据库总大小的 1.2 倍可用空间。导出会读取全库；观察主库磁盘余量、复制延迟和 readiness，
避免与索引建设、清理大表等重负载重叠。备份过程中不得修改角色、密钥或运行时配置：这些文件和数据库
不是一个跨系统原子快照。主库切换、连接中断或失败时保留 `.partial` 和日志，不自动重试。

备份目录和文件分别限制为 0700、0600，但**不额外加密**；角色密码、应用加密密钥、证书均在其中，
应存放在受控加密磁盘。不要上传 Git、工单或公开报告。`manifest.json` 记录哈希和完成状态。
`runtime.tar.gz` 仅含指定节点配置，灾难恢复时必须按新节点地址重新渲染，不能原样覆盖其他节点。
这份备份不包括 NATS 消息队列、其他节点的独有配置，也不构成完整集群恢复验收。

恢复脚本校验三份文件哈希，然后创建无网络、无宿主机端口的独立数据库容器和唯一数据卷，
恢复角色、数据、索引、约束与权限。验收记录行数、事件时间范围、无效索引数量；成功后仍不启动应用，
也不触碰生产数据库。结束时删除临时容器和数据卷，报告必须同时检查 `status=complete` 和
`temporary_volume_removed=true`。恢复日志存在时拒绝覆盖；重验前另存旧日志和报告。
进程被强制杀死或机器断电时，按报告和 `openxdr-restore-*` 名称核对残留后手动清理。

该流程证明备份可被 PostgreSQL 恢复，不证明整站切换或业务流程恢复。
未开启 WAL 归档时不能恢复到任意时间点；故障后的数据损失窗口取决于最后一份成功备份。
定期任务、异地副本、保留策略及告警需根据长期备份目的地另行配置。

## 容量处理顺序

1. 确认可恢复备份，再扩容两台数据库节点并验证磁盘、文件系统和复制状态。
2. 根据实际写入速率与保留需求计算容量；普通表 DELETE 只提供可重用空间，通常不减少文件大小。
3. 有足够临时空间、维护窗口和回退路径后，评估 `docs/event-partitioning.md` 的在线迁移。
4. 不在高水位磁盘上直接运行 `VACUUM FULL`、大表复制或重复建设索引。

## 2026-10-22 实测

对 83.7GiB 的 PostgreSQL 16.14 生产库完成一次节点外逻辑备份，数据库归档为
5,691,070,789 字节，导出约 8 分 50 秒。三份备份的 SHA256 校验通过。
在无网络的 PostgreSQL 16 临时容器中完整恢复数据、索引、约束和角色授权，耗时约 54 分钟：

| 检查 | 结果 |
| --- | ---: |
| events | 74,583,982 |
| assets | 4 |
| incidents | 172 |
| commands | 920 |
| settings | 12 |
| 无效索引 | 0 |

事件范围为 2026-08-12 05:01:33 UTC 至 2026-10-22 09:16:27 UTC。
临时容器和数据卷均已清理。首次尝试暴露了角色授权者与临时初始化用户不一致的问题，
修正为使用原 `postgres` 授权者、仅跳过其重复 CREATE ROLE 后，上述重验通过。

这次主要耗时来自原始日志 GIN 索引重建，不应把导出时间作为恢复时间承诺。
生产主库磁盘仍约 90%，未执行分区迁移或回收大表文件；WAL 归档、定期备份和异地保留策略尚未启用。
新飞书通知配置在备份之后保存，另存私有配置补充，未包含在本次数据库快照中。
